Grand Hotel Kielce Availability Leak

Target: reservations.grandhotelkielce.pl (Bookassist engine, hotel 4014 / guide 823) Tested: 30 September 2026 Window: nights of 1 to 14 October 2026
Confirmed: any visitor can read how many rooms of each type are left. The page's own background call to /api/engineResult returns a field named lowestAvailabilities with a live count per room group. The interface never shows these numbers, but they are in the JSON for every search. Combined with the total room count that /api/engineCheck also returns, this gives a night-by-night occupancy estimate for the hotel.

What the page does under the hood

The site is a Next.js front end over the Bookassist engine. Opening the "choose rooms" page fires this sequence. Everything in bold below is readable in any browser's network tab.

  1. GET /__ENV.jsFront-end configuration: CDN hosts, Microsoft Clarity id, Google Maps API key.
  2. GET /api/engineCheckHotel configuration: total rooms, booking mailboxes, 80 feature flags, backend session ids and egress IP.
  3. GET /api/engineResultRates for the searched dates, plus lowestAvailabilities, per-day stop-sell flags, rack rates and discount rules.
  4. GET /api/roomStuff, /api/roomConfigPer-rate descriptions and occupancy rules, one call per rate shown.
  5. POST /api/spoorBookassist analytics: visitor IP, user agent, ad-block flag, fingerprint id and the full cookie string.
  6. GET webapi-prod.bookassist.com/…/i18n/…Translation bundles, fetched directly from the vendor.

Findings

● Critical Remaining rooms per type are exposed on every search

Response of /api/engineResult, top level. The keys are room-group ids that the same response maps to names in roomPrices[]. The values change from night to night and sum, at their peaks, to the hotel's capacity, which shows they are live inventory rather than a static setting.

"lowestAvailabilities": {"22742": 31, "22743": 27, "22744": 8, "22745": 35, "22746": 9, "22747": 1, "22748": 2}   // night of 9 Oct
  • Impact: competitors, rate-shopping tools and online travel agents can build an occupancy calendar for the hotel with one request per night.
  • Also in the same response: notBookableReasons[].cause = "STOP_SELL" with the date, and per-day stopSale, closeForArrival, minNights, rackRef (rack rate) and dynamicDiscountId.

● Serious Total capacity, booking mailbox and internal configuration are exposed

Response of /api/engineCheck, object engine.hotel and engine.hotelOptions.

"hotel": { "numberOfRooms": 122, "numberOfSuites": 0, "bookingEmail": "hotel@grandhotelkielce.pl", "voucherEmail": "hotel@grandhotelkielce.pl",
           "minHoursAhead": 0, "maxMonthBookAhead": 36, "maxStayNights": 365, "bookitLevel": 2, … }
"hotelOptions": { "maxRoomsPerBooking": -1, "useDynamicDiscount": …, "canAmendBooking": …, "tripteaseToken": "", … }   // ~80 flags
  • The room total is what turns per-type counts into an occupancy percentage.
  • The response also carries an empty customer template whose field names include password, which suggests the same object is reused for logged-in customers server side.

● Low Backend details leak: server IP, session ids, a localhost origin, an API key

  • engine.identity.ip and analytics.clientIP report the Next.js server's own egress address (user agent "node"), not the visitor's, together with sessionId, baSessionId, uuid and a gzip-encoded hash blob.
  • The first redirect sets a cookie bp4014_823 whose value begins with https://localhost:3000/, a development origin left in production.
  • /__ENV.js publishes the Google Maps browser key. That is acceptable only if the key is restricted by HTTP referrer in Google Cloud Console.
  • /api/spoor sends the visitor's full cookie string and a fingerprint id to Bookassist analytics. Check that the privacy notice covers it.

● Not confirmed Plain HTTP replay without a browser

Replaying the page's own three calls (page, engineCheck, engineResult) with a plain Python HTTP client returned engineResult returned 500, so the API expects something the front end adds. A headless browser receives the full JSON, so this is friction rather than a control. It raises the cost of scraping slightly and does not change the findings above.

What to ask Bookassist to change

  1. Remove lowestAvailabilities from the public response, or reduce it to a boolean or a capped value such as "3+" that the interface actually needs.
  2. Strip hotel.numberOfRooms, numberOfSuites, bookingEmail and voucherEmail from engineCheck; the front end does not render them.
  3. Replace raw cause codes and per-day revenue-management fields (STOP_SELL, stopSale, closeForArrival, rackRef) with the customer-facing message only.
  4. Drop identity.ip, session identifiers and the hash blob from the client payload, and fix the cookie that references localhost:3000.
  5. On your side: restrict the Google Maps key to the reservations domain, and review the analytics payload against the privacy notice.

Method and limits

All observations come from loading the public booking page in a headless Chromium browser and recording the responses it receives, exactly as a visitor's browser would. The two-week board used one page load per night, sequentially, with a two-second pause between loads. No other hotels, no vendor endpoints beyond what the page itself calls, and no booking or payment steps were touched. The numbers are a snapshot from the evening of 30 September 2026 and will have changed since.

Scripts: 01_capture.py (full network capture of one search), 02_confirm_plain_http.py (plain-client replay), 03_two_weeks.py (the fourteen-night board), 04_build_report.py (this page). They live in the repository branch claude/hotel-info-leakage-test-sypq7u under hotel-leakage-test/.
